**Superseded (2026-11-20):** the `winui-immediate` crate replaces this spike,
and its plan of record is `plans/winui-immediate.md` (WP-00 to WP-08 done).
The crate keeps the spike's findings below and changes the mechanisms: drop
on detach in place of a global prune, 5 shared delegates in place of a
closure per control, `ItemsRepeater` only, explicit `cached`/`state`/
`list_state` nodes, a typed mailbox, and `tracing` logs. Its example
`winui-immediate/examples/vault_list.rs` measures 0 UI-thread allocations
per steady pass and realize p50 20 µs; `winui-immediate/tests/ui/*.ps1`
replaces the spike's scripts. The vault app's shell builds on the crate
(`plans/sans-io-vault-core.md`). Read this note for why the crate looks as
it does, and the crate's plan for how it works now.

Spike in `spikes/src/bin/immediate/` (`main.rs`, `ui.rs`, `winui.rs`,
`winui/bindings.rs`), moved there from `src/bin/immediate/`. No Reactor. It answers whether a RAD debugger style API
(rebuild everything on each event, keyed widget cache, diff to WinUI setters)
works over the WinUI retained tree.

## How it is built

- Bindings: windows-bindgen 0.100 in `--minimal` mode, from the installed
  `Microsoft.WindowsAppRuntime.2_2.4.0.0_x64` winmd files, generated by
  `tools/winui-bindgen` (`cargo run --release -- <winmd folder> <out.rs>`) from
  `tools/winui-bindgen/filter.txt`. Minimal mode emits only members the filter names
  (`Type::{get_X, put_X, add_E, remove_E}`); a sealed or activatable class needs
  `Type::CreateInstance` to get `new()`; inherited members need `.cast()` (for
  example `ButtonBase::Click`, `ContentControl::SetContent`). `--compose` needs
  `IApplicationFactory` in the filter. `rustfmt` must be on PATH
  (`~/.cargo/bin` is not on the agent shell's PATH).
- Startup copies Reactor 0.100: `TryCreatePackageDependency` +
  `AddPackageDependency`, STA, `Application::compose` with
  `IApplicationOverrides` + `IXamlMetadataProvider`. `XamlControlsResources`
  must be merged in `OnLaunched`; doing it in the `Start` callback fails with
  `E_UNEXPECTED`.
- Layer: key = FxHash(parent key, local id). Cache node keeps the WinUI handle,
  the last value written, the child key list. Build diffs each container's
  child list (prefix/suffix for stacks, set difference for the canvas), prunes
  untouched nodes. Events are `(key, event)` pushed by WinUI handlers, and a
  `DispatcherQueue` callback coalesces rebuilds.
- User-edited values (TextBox text) are read back on `TextChanged` and written
  only when the app changed them. Password stays in the `PasswordBox` and is
  read once by `take_password` on submit (threat model option A).
- List: `ScrollViewer` + `Canvas`, fixed 32 px rows, only visible rows plus 4
  overscan are built, keyed by entry id, placed with `Canvas.SetTop`.

## Measured (release, 1,000 entries, about 24 rows built)

| Build where… | p50 | p90 | Allocations | WinUI calls |
|---|---|---|---|---|
| nothing changed | 5 µs | 7 µs | 0 | 2 (scroll reads) |
| one row's name changed | 4 µs | 4 µs | 0.1 | 3 |
| every name changed | 11 µs | 21 µs | 0.1 | 25 |
| scrolled one row | 36 µs | 52 µs | 5 | 11, 4 widgets created and dropped |
| first build | 14–20 ms | | 144 | 223 |

Times cover our build and diff only, not WinUI layout or render. Reactor's
numbers in [[windows-reactor-pitfalls]] rendered all 1,000 rows, so they are
not directly comparable.

## Verified through UI Automation

- Typing "entry 12", Left, "3" while rebuilding every 10 ms gives
  "entry 132": caret survives rebuilds, and the app saw all 9 edits.
- Reveal shows the row's password; Unlock with a typed password flips to Lock.

- **IME:** `SPIKE_IME=vi` activates Vietnamese Telex for the spike process
  only (TSF `ActivateProfile` with `TF_IPPMF_FORPROCESS`, raw COM in
  `ime.rs`; the bindgen default Win32 metadata did not resolve TSF names).
  Typing `tieesng vieetj` gives `tiếng việt`, with and without a trailing
  commit space, with and without rebuilds every 10 ms: 12 of 12 runs correct.
  One earlier run without the timer lost the second word, most likely because
  the IME was not active yet.
- **Real scrolling** (UI Automation `ScrollPattern`, 1,000 rows of 32 px): after
  a jump to 50%, 60 small steps, 20 page steps and a jump to the end, the rows
  on screen were consecutive entries covering the whole viewport every time.

## Cost of real scrolling (`SPIKE_LOG=1`)

| Build that… | p50 | Note |
|---|---|---|
| adds one row (4 controls) | 180 µs | about 45 µs per created control |
| drops one row | 500 µs | detach with `IndexOf` + `RemoveAt`, revoke, release |
| replaces about 20 rows (page step) | 3.3 ms | |
| first build | 14 ms | 100 controls |

Creating and dropping controls dominates. The diff itself costs 5–36 µs
(bench).

## Row reuse: three list modes (`SPIKE_LIST=canvas|pool|repeater`)

- **canvas**: rows keyed by entry id, created and dropped while scrolling.
- **pool** (option B): each entry in view owns a slot; row keys are
  `hash(canvas, ("slot", n))`, so a slot's controls are reused when one entry
  leaves and another enters. Free slots stay in the canvas, `Collapsed`, so
  reuse costs `Visibility` + `Canvas.Top` + text, with no detach.
- **repeater**: WinUI `ItemsRepeater` with a fake `ItemsSource` of boxed
  indexes and our own `IElementFactory` (`RowFactory` in `ui.rs`).
  `GetElement` builds the row synchronously through `REPEATER_HOOKS` (no empty
  shell step, unlike Reactor), reusing a recycled row's controls.
  `RecycleElement` returns the row to the list's pool. Each top-down build
  rebuilds realized rows and keeps recycled rows alive. `SetItemsSource` runs
  after the build with every `RefCell` released, because WinUI may call the
  factory inside it. `revision` (bumped on refilter) resets the source.

UI Automation scroll test (jump 50%, 60 small steps, 20 page steps, jump to
end), all three modes showed consecutive rows covering the viewport:

| Mode | Build p50 | Build p90 | Controls created in the whole test |
|---|---|---|---|
| canvas | 477 µs | 3.3 ms | 1,924 |
| pool | 66 µs | 175 µs | 120 |
| repeater | 47 µs (plus 544 realizes, p50 18 µs, max 122 µs) | 51 µs | 252 |

Click (Reveal, Unlock) and filter-while-rebuilding tests pass in pool and
repeater modes; the repeater's filter path exercises the source reset.

Caveat: `SPIKE_BENCH` is not valid for the repeater. The back-to-back bench
builds run before any layout pass, so the repeater realizes no rows (it
reports 8 widgets, 0 calls).

Open hazards, untested: focus inside a pooled or recycled row; a click queued
for a slot that is reassigned before the next build; rows of different
heights in the repeater (it supports them, the test rows are fixed).

## Findings

- **One-build lag is real.** A click read late in a build does not update
  widgets built earlier in it. Fix used: run one more build whenever a build
  consumed events. Without it both click checks failed.
- **Not tested:** IME while the app rewrites the text during composition,
  variable-height rows, WinUI layout and render cost, and other IMEs (only
  Vietnamese Telex is installed here).

**Why:** the user prefers plain `&mut App` code over Reactor's component and
message model, and asked for this spike to judge the trade-off.

**How to apply:** use the `winui-immediate` crate, not this spike, for new
UI work. See [[windows-reactor-internals]] for the rejected alternative.
